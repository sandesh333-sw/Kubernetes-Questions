# 🗓️ **WEEK 3 – Scaling, Probes & Health Checks**

## 📚 **Theory & Q&A**

### 1. How do you scale Pods manually?

> Use `kubectl scale` command to manually change the number of replicas in a Deployment, ReplicaSet, or StatefulSet.

**Command:**
```bash
kubectl scale deployment myapp --replicas=5
```

**Using YAML:**
```bash
kubectl edit deployment myapp
# Change spec.replicas: 5
```

**Declarative approach:**
```yaml
spec:
  replicas: 5
```

Then apply: `kubectl apply -f deployment.yaml`

---

### 2. What is the Horizontal Pod Autoscaler (HPA)?

> **HPA** automatically scales the number of Pods based on observed metrics like:
> - CPU utilization
> - Memory utilization
> - Custom metrics (requests per second, queue length, etc.)

**How it works:**
1. Metrics Server collects resource metrics
2. HPA controller checks metrics periodically (default: 15s)
3. Calculates desired replicas based on target metric
4. Scales the Deployment/ReplicaSet

**Formula:**
```
desiredReplicas = ceil[currentReplicas * (currentMetric / targetMetric)]
```

**Example:**
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

**Creating HPA with kubectl:**
```bash
kubectl autoscale deployment myapp --cpu-percent=70 --min=2 --max=10
```

### 3. What is a Readiness Probe?

> **Readiness Probe** checks if a container is **ready to receive traffic**.
> 
> **Key Points:**
> - If it fails, the Pod is removed from Service endpoints (no traffic sent)
> - Pod remains running, just doesn't receive requests
> - Useful for apps that need warm-up time

**Use Cases:**
- Application startup (loading cache, connecting to database)
- Temporary overload (too many requests, recovering)
- Dependencies not ready (database down, API unavailable)

**Types:**
1. **HTTP GET** - Sends HTTP request, expects 200-399 status code
2. **TCP Socket** - Tries to open TCP connection
3. **Exec** - Runs command, expects exit code 0

**Example - HTTP:**
```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
  failureThreshold: 3
  successThreshold: 1
```

---

### 4. What is a Liveness Probe?

> **Liveness Probe** checks if the container is **alive and healthy**.
> 
> **Key Points:**
> - If it fails, Kubernetes **restarts the container**
> - Used to recover from deadlocks or hung processes
> - Too aggressive = restart loops

**Use Cases:**
- Deadlocks (application stuck)
- Out of memory (application not responding)
- Critical error states

**Example - HTTP:**
```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 20
  failureThreshold: 3
```

**Example - TCP:**
```yaml
livenessProbe:
  tcpSocket:
    port: 3306
  initialDelaySeconds: 15
  periodSeconds: 10
```

**Example - Exec:**
```yaml
livenessProbe:
  exec:
    command:
    - cat
    - /tmp/healthy
  initialDelaySeconds: 5
  periodSeconds: 5
```

---

### 5. What is a Startup Probe?

> **Startup Probe** is used for containers that take a long time to start.
> 
> **Key Points:**
> - Disables liveness and readiness checks until it succeeds
> - Prevents liveness probe from killing slow-starting containers
> - Once succeeds, liveness/readiness probes take over

**Use Case:** Legacy apps with slow initialization (30+ seconds)

**Example:**
```yaml
startupProbe:
  httpGet:
    path: /health/startup
    port: 8080
  initialDelaySeconds: 0
  periodSeconds: 10
  failureThreshold: 30  # 10s * 30 = 300s (5 minutes)
```

---

### 6. Probe Configuration Parameters

| Parameter             | Description                                  | Default |
| --------------------- | -------------------------------------------- | ------- |
| `initialDelaySeconds` | Wait before first probe                      | 0       |
| `periodSeconds`       | How often to probe                           | 10      |
| `timeoutSeconds`      | Probe timeout                                | 1       |
| `successThreshold`    | Minimum consecutive successes                | 1       |
| `failureThreshold`    | Consecutive failures before action           | 3       |

**Example with all parameters:**
```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 3000
  initialDelaySeconds: 30
  periodSeconds: 15
  timeoutSeconds: 5
  successThreshold: 1
  failureThreshold: 3
```

### 7. What are Resource Requests and Limits?

> **Requests** = Minimum resources guaranteed to container
> **Limits** = Maximum resources container can use

**CPU:**
- Measured in cores (1 = 1 vCPU)
- Can use milicores: 100m = 0.1 CPU
- Request: Scheduling decision
- Limit: Throttled if exceeded

**Memory:**
- Measured in bytes (Ki, Mi, Gi)
- Request: Scheduling decision
- Limit: OOMKilled if exceeded

**Example:**
```yaml
resources:
  requests:
    memory: "64Mi"
    cpu: "250m"      # 0.25 CPU
  limits:
    memory: "128Mi"
    cpu: "500m"      # 0.5 CPU
```

---

### 8. What happens if a Pod exceeds its limit?

**CPU Limit Exceeded:**
- Container is **throttled** (slowed down)
- Not killed, just gets less CPU time
- Performance degrades

**Memory Limit Exceeded:**
- Container is **OOMKilled** (Out Of Memory Killed)
- Pod status shows `OOMKilled`
- Container restarts (based on `restartPolicy`)

**No Limits Set:**
- Container can consume all available resources
- Can starve other Pods on the same node
- Cluster instability

---

### 9. Quality of Service (QoS) Classes

Kubernetes assigns QoS class based on requests/limits:

| QoS Class    | Condition                              | Eviction Priority |
| ------------ | -------------------------------------- | ----------------- |
| Guaranteed   | requests = limits (for all containers) | Lowest (last)     |
| Burstable    | At least one request/limit set         | Medium            |
| BestEffort   | No requests/limits set                 | Highest (first)   |

**Guaranteed:**
```yaml
resources:
  requests:
    memory: "128Mi"
    cpu: "500m"
  limits:
    memory: "128Mi"
    cpu: "500m"
```

**Burstable:**
```yaml
resources:
  requests:
    memory: "64Mi"
    cpu: "250m"
  limits:
    memory: "128Mi"
    cpu: "500m"
```

**BestEffort:**
```yaml
# No resources defined
```

### 10. What is a Rolling Update?

> **Rolling Update** gradually replaces old Pods with new ones **without downtime**.

**Process:**
1. Create new ReplicaSet with updated image
2. Scale up new ReplicaSet (create new Pods)
3. Scale down old ReplicaSet (delete old Pods)
4. Repeat until all Pods are updated

**Strategy:**
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1        # Max new Pods during update
    maxUnavailable: 0  # Max unavailable Pods during update
```

**Example:**
- Current: 4 Pods
- maxSurge: 1 → Can create 5th Pod
- maxUnavailable: 0 → All 4 old Pods stay until new ones ready
- Process: 4 → 5 → 4 → 5 → 4 (gradually replace)

---

### 11. How do you rollback a Deployment?

**View rollout history:**
```bash
kubectl rollout history deployment myapp
```

**Rollback to previous version:**
```bash
kubectl rollout undo deployment myapp
```

**Rollback to specific revision:**
```bash
kubectl rollout undo deployment myapp --to-revision=2
```

**Check rollout status:**
```bash
kubectl rollout status deployment myapp
```

**Pause/Resume rollout:**
```bash
kubectl rollout pause deployment myapp
kubectl rollout resume deployment myapp
```

---

### 12. Deployment Update Strategies

**1. RollingUpdate (default):**
- Zero downtime
- Gradual replacement
- Can rollback

**2. Recreate:**
- Kill all old Pods first
- Then create new Pods
- Causes downtime
- Useful when running both versions simultaneously is problematic

```yaml
strategy:
  type: Recreate
```

### 13. What is a DaemonSet?

> **DaemonSet** ensures one Pod runs on **every node** (or selected nodes).

**Use Cases:**
- Log collectors (Fluentd, Logstash)
- Monitoring agents (Node Exporter, Datadog)
- Network plugins (Calico, Weave)
- Storage daemons (Ceph, GlusterFS)

**Characteristics:**
- Automatically adds Pod to new nodes
- Removes Pod when node is removed
- Ignores `replicas` field (1 per node)

**Example:**
```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
spec:
  selector:
    matchLabels:
      app: node-exporter
  template:
    metadata:
      labels:
        app: node-exporter
    spec:
      containers:
      - name: node-exporter
        image: prom/node-exporter:latest
        ports:
        - containerPort: 9100
```

**DaemonSet on specific nodes:**
```yaml
spec:
  template:
    spec:
      nodeSelector:
        disktype: ssd
```

### 14. What is a StatefulSet?

> **StatefulSet** manages Pods with **persistent identity and stable storage**.

**Differences from Deployment:**

| Feature           | Deployment        | StatefulSet              |
| ----------------- | ----------------- | ------------------------ |
| Pod names         | Random hash       | Ordered (app-0, app-1)   |
| Pod restart       | Any name          | Same name                |
| Storage           | Shared or none    | Individual PVC per Pod   |
| Creation order    | Parallel          | Sequential (0, 1, 2...)  |
| Deletion order    | Random            | Reverse (2, 1, 0...)     |
| Network identity  | Random IP         | Stable DNS name          |

**Use Cases:**
- Databases (MySQL, PostgreSQL, MongoDB)
- Distributed systems (ZooKeeper, Kafka, Elasticsearch)
- Applications requiring stable network identity

**Example:**
```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        ports:
        - containerPort: 3306
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 10Gi
```

**Pod names:** `mysql-0`, `mysql-1`, `mysql-2`
**DNS names:** `mysql-0.mysql`, `mysql-1.mysql`, `mysql-2.mysql`

---

### 15. What is a ReplicaSet?

> **ReplicaSet** ensures a specified number of identical Pods are running.

**Key Points:**
- Usually managed by Deployment (don't create directly)
- Maintains desired replica count
- Replaces failed Pods
- Selector-based Pod management

**You rarely create ReplicaSets directly - use Deployments instead!**

## 🔥 **Pro Tips & Best Practices**

### Scaling
✅ **DO:**
- Use HPA for automatic scaling
- Set reasonable min/max replicas
- Test scaling behavior under load
- Monitor metrics before autoscaling

❌ **DON'T:**
- Over-provision (waste resources)
- Set HPA min=max (defeats purpose)
- Scale based on single metric only
- Forget to install Metrics Server

### Probes
✅ **DO:**
- Use all three probes (liveness, readiness, startup)
- Set appropriate delays and thresholds
- Make probe endpoints lightweight
- Different endpoints for liveness vs readiness

❌ **DON'T:**
- Make probes too aggressive (restart loops)
- Use same endpoint for liveness and readiness
- Probe external dependencies in liveness
- Skip startup probe for slow apps

### Resource Management
✅ **DO:**
- Always set requests for production
- Set limits to prevent resource hogging
- Use namespace ResourceQuotas
- Monitor actual usage and adjust

❌ **DON'T:**
- Set limits = requests unnecessarily
- Forget memory limits (OOMKill risk)
- Over-provision requests (waste)
- Skip resource monitoring

### Deployments
✅ **DO:**
- Use rolling updates
- Set maxUnavailable and maxSurge
- Test rollback procedure
- Use revision annotations

❌ **DON'T:**
- Use Recreate unless necessary
- Skip rollout testing
- Deploy without readiness probes
- Ignore failed rollouts

## 📝 **Common Interview Questions**

**Q: Difference between Liveness and Readiness probes?**
> - **Liveness**: Is container alive? (restart if fails)
> - **Readiness**: Is container ready for traffic? (remove from service if fails)

**Q: When would you use a Startup Probe?**
> For legacy apps with slow initialization that might trigger liveness probe failures during startup.

**Q: What happens if you don't set resource requests?**
> - Pod might be scheduled on any node
> - No guaranteed resources
> - QoS class = BestEffort
> - First to be evicted under pressure

**Q: Difference between maxSurge and maxUnavailable?**
> - **maxSurge**: Max new Pods during update (capacity buffer)
> - **maxUnavailable**: Max Pods that can be unavailable (maintains minimum)

**Q: Can HPA scale to 0?**
> No, minimum replicas must be >= 1. Use KEDA (Kubernetes Event-Driven Autoscaling) for scale-to-zero.

**Q: What is the difference between DaemonSet and Deployment?**
> - **DaemonSet**: One Pod per node (ignore replicas)
> - **Deployment**: Specified replicas, scheduled anywhere

**Q: How does StatefulSet maintain Pod identity?**
> - Ordinal naming (app-0, app-1)
> - Stable DNS names
> - Individual PVCs
> - Sequential creation/deletion

**Q: What is Pod Disruption Budget (PDB)?**
> Limits the number of Pods that can be down simultaneously during voluntary disruptions (node drain, updates).

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: myapp-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: myapp
```
