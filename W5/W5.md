# 🗓️ **WEEK 5 – Helm, CRDs, and Operators**

## 📚 **Theory & Q&A**

### 1. What is Helm?

> **Helm** is a package manager for Kubernetes - like apt/yum for Linux or npm for Node.js.
> 
> It packages Kubernetes resources into reusable, versioned bundles called **Charts**.

**Problems Helm Solves:**
- Managing dozens of YAML files
- Version control and rollbacks
- Configuration management (dev, staging, prod)
- Sharing and reusing Kubernetes applications
- Template-based deployment

**Benefits:**
- ✅ One command to install complex applications
- ✅ Parameterized templates (values.yaml)
- ✅ Easy upgrades and rollbacks
- ✅ Dependency management
- ✅ Release history

---

### 2. What's a Helm Chart?

> A **Helm Chart** is a collection of YAML templates and configurations that define a Kubernetes application.

**Chart Structure:**
```
mychart/
├── Chart.yaml          # Chart metadata (name, version)
├── values.yaml         # Default configuration values
├── charts/             # Chart dependencies
├── templates/          # Kubernetes manifest templates
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   ├── _helpers.tpl    # Template helpers
│   └── NOTES.txt       # Post-install notes
└── README.md           # Documentation
```

**Chart.yaml Example:**
```yaml
apiVersion: v2
name: myapp
description: A Helm chart for my application
version: 1.0.0          # Chart version
appVersion: "2.0.0"     # Application version
```

### 3. How do you install an app using Helm?

**From Helm repository:**
```bash
# Add repo
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update

# Search
helm search repo mongodb

# Install
helm install my-mongodb bitnami/mongodb
```

**From local chart:**
```bash
helm install my-release ./mychart
```

**With custom values:**
```bash
# Override with file
helm install my-release ./mychart -f custom-values.yaml

# Override with --set
helm install my-release ./mychart \
  --set replicaCount=3 \
  --set image.tag=v2.0
```

**In specific namespace:**
```bash
helm install my-release ./mychart -n production --create-namespace
```

### 5. What are Template Functions in Helm?

> Helm uses **Go templates** with additional functions from **Sprig** library.

**Common Template Functions:**

**1. Values:**
```yaml
# values.yaml
replicaCount: 3
image:
  repository: nginx
  tag: "1.24"

# In template
replicas: {{ .Values.replicaCount }}
image: {{ .Values.image.repository }}:{{ .Values.image.tag }}
```

**2. Built-in Objects:**
```yaml
# .Release - info about release
{{ .Release.Name }}
{{ .Release.Namespace }}
{{ .Release.Service }}

# .Chart - Chart.yaml content
{{ .Chart.Name }}
{{ .Chart.Version }}

# .Capabilities - cluster capabilities
{{ .Capabilities.KubeVersion }}
```

**3. String Functions:**
```yaml
{{ .Values.name | upper }}           # UPPERCASE
{{ .Values.name | lower }}           # lowercase
{{ .Values.name | title }}           # Title Case
{{ .Values.name | quote }}           # "quoted"
{{ .Values.name | default "default" }} # Default value
```

**4. Conditionals:**
```yaml
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
# ...
{{- end }}
```

**5. Loops:**
```yaml
{{- range .Values.env }}
- name: {{ .name }}
  value: {{ .value }}
{{- end }}
```

### 6. How do you upgrade a Helm release?

```bash
# Upgrade with new values
helm upgrade my-release ./mychart -f new-values.yaml

# Upgrade with --set
helm upgrade my-release ./mychart --set image.tag=v2.0

# Dry run (test without applying)
helm upgrade my-release ./mychart --dry-run --debug

# Force recreation of resources
helm upgrade my-release ./mychart --force

# Wait for resources to be ready
helm upgrade my-release ./mychart --wait --timeout 5m
```

---

### 7. How do you rollback a Helm release?

```bash
# View release history
helm history my-release

# Rollback to previous version
helm rollback my-release

# Rollback to specific revision
helm rollback my-release 3

# Rollback with dry run
helm rollback my-release 3 --dry-run
```

### 8. What's the benefit of Helm over raw YAML?

| Aspect                 | Raw YAML                          | Helm                               |
| ---------------------- | --------------------------------- | ---------------------------------- |
| **Reusability**        | Copy-paste, find-replace          | Parameterized templates            |
| **Versioning**         | Git tags                          | Built-in release versioning        |
| **Upgrades**           | Manual kubectl apply              | helm upgrade (with history)        |
| **Rollbacks**          | Manual (git revert + apply)       | helm rollback (one command)        |
| **Configuration**      | Multiple files per environment    | Single values file                 |
| **Dependencies**       | Manual management                 | Automatic dependency resolution    |
| **Sharing**            | Git repos                         | Helm repositories                  |
| **Documentation**      | Separate README                   | Built-in NOTES.txt                 |

### 9. What are Custom Resource Definitions (CRDs)?

> **CRDs** allow you to **extend Kubernetes API** with your own custom resources.

**Example:**
```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.example.com
spec:
  group: example.com
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              size:
                type: string
              version:
                type: string
  scope: Namespaced
  names:
    plural: databases
    singular: database
    kind: Database
    shortNames:
    - db
```

**Once CRD is created, you can create custom resources:**
```yaml
apiVersion: example.com/v1
kind: Database
metadata:
  name: my-database
spec:
  size: 10Gi
  version: "15"
```

**Use Cases:**
- Custom applications (databases, message queues)
- Platform extensions
- Policy management
- CI/CD pipelines

### 10. What are Operators?

> **Operators** are applications that **manage other applications** using CRDs and custom controllers.

**Operator = CRD + Controller + Domain Knowledge**

**How Operators Work:**
1. Define CRD (e.g., `PostgresCluster`)
2. User creates custom resource
3. Operator watches for custom resources
4. Operator performs actions (create Pods, PVCs, Services, backups, etc.)
5. Operator continuously reconciles desired vs actual state

**Example Operators:**
- **Prometheus Operator** - Manages Prometheus instances
- **MySQL Operator** - Manages MySQL clusters
- **Cert-Manager** - Manages TLS certificates
- **ArgoCD** - GitOps deployment
- **Vault Operator** - Manages HashiCorp Vault

**Benefits:**
- Automates complex operations
- Encapsulates domain knowledge
- Self-healing
- Automated backups and upgrades
- Day-2 operations (scaling, updates, maintenance)

---

### 11. Difference between CRD and Operator?

| Aspect          | CRD                                | Operator                          |
| --------------- | ---------------------------------- | --------------------------------- |
| **What**        | Custom resource definition         | CRD + Controller logic            |
| **Purpose**     | Define *what* (schema)             | Define *how* (automation)         |
| **Components**  | API definition only                | CRD + Controller + Logic          |
| **Behavior**    | None (just data)                   | Active reconciliation             |
| **Example**     | `kind: Database`                   | Controller that creates DB Pods   |

**Analogy:**
- **CRD**: Blueprint of a car
- **Operator**: Factory that builds the car, maintains it, and repairs it

### 12. How can you version-control Helm charts?

**Methods:**

**1. Git Repository:**
```bash
# Chart source in Git
myapp-chart/
├── Chart.yaml
├── values.yaml
└── templates/

# Version via Chart.yaml
version: 1.0.0
```

**2. Helm Repository:**
```bash
# Package chart
helm package myapp-chart

# Upload to repository (S3, GCS, ChartMuseum, etc.)
# Or use GitHub Pages, Nexus, Artifactory

# Index repository
helm repo index .
```

**3. OCI Registry (Docker registry):**
```bash
# Package and push to OCI registry
helm package myapp-chart
helm push myapp-chart-1.0.0.tgz oci://registry.example.com/charts

# Install from OCI
helm install my-release oci://registry.example.com/charts/myapp-chart --version 1.0.0
```

### 13. Helm Hooks

> **Hooks** allow you to run jobs at specific points in release lifecycle.

**Available Hooks:**
- `pre-install` - Before any resources are created
- `post-install` - After all resources are created
- `pre-delete` - Before any resources are deleted
- `post-delete` - After all resources are deleted
- `pre-upgrade` - Before upgrade
- `post-upgrade` - After upgrade
- `pre-rollback` - Before rollback
- `post-rollback` - After rollback

**Example:**
```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
  annotations:
    "helm.sh/hook": pre-upgrade
    "helm.sh/hook-weight": "1"
    "helm.sh/hook-delete-policy": hook-succeeded
spec:
  template:
    spec:
      containers:
      - name: migrate
        image: myapp:latest
        command: ["./migrate.sh"]
      restartPolicy: Never
```

### 14. What is the Operator Pattern?

> **Operator Pattern** extends Kubernetes to automate management of complex, stateful applications.

**Operator Levels (Capability Model):**

| Level | Capability                    | Examples                          |
| ----- | ----------------------------- | --------------------------------- |
| 1     | Basic Install                 | Deploy resources                  |
| 2     | Seamless Upgrades             | Automated updates                 |
| 3     | Full Lifecycle                | Backup, restore, failure recovery |
| 4     | Deep Insights                 | Metrics, alerts, tuning           |
| 5     | Auto Pilot                    | Self-healing, scaling, tuning     |

**Popular Operator Frameworks:**
- **Operator SDK** (Red Hat) - Go, Ansible, Helm
- **Kubebuilder** (Kubernetes SIG) - Go
- **KUDO** - Declarative operators
- **Kopf** - Python operators

### 15. Helm Chart Dependencies

**Chart.yaml with dependencies:**
```yaml
apiVersion: v2
name: myapp
version: 1.0.0
dependencies:
- name: postgresql
  version: 12.1.0
  repository: https://charts.bitnami.com/bitnami
  condition: postgresql.enabled
- name: redis
  version: 17.0.0
  repository: https://charts.bitnami.com/bitnami
  condition: redis.enabled
```

**Update dependencies:**
```bash
helm dependency update ./myapp
```

**Override dependency values:**
```yaml
# values.yaml
postgresql:
  enabled: true
  auth:
    username: myuser
    password: mypassword
    database: mydb

redis:
  enabled: true
  auth:
    enabled: false
```

## 🔥 **Pro Tips & Best Practices**

### Helm
✅ **DO:**
- Use versioning (semantic versioning)
- Lint charts before packaging
- Use values.yaml for configuration
- Document charts with README and NOTES.txt
- Test with `--dry-run` first
- Use namespaces for isolation

❌ **DON'T:**
- Hard-code values in templates
- Skip version bumps
- Ignore helm lint warnings
- Deploy without testing
- Use `--force` without understanding why

### CRDs & Operators
✅ **DO:**
- Use OpenAPI validation schemas
- Version your CRDs (v1alpha1, v1beta1, v1)
- Document CRD fields
- Test operator reconciliation loops
- Implement proper error handling
- Use operator frameworks (don't write from scratch)

❌ **DON'T:**
- Create CRDs without validation
- Skip CRD upgrades (breaking changes)
- Make operators too complex
- Forget RBAC permissions
- Ignore resource cleanup

## 📝 **Common Interview Questions**

**Q: What is Helm and why use it?**
> Helm is a package manager for Kubernetes. It simplifies deployment, versioning, and management of applications through templating and release management.

**Q: Explain Helm chart structure.**
> Chart.yaml (metadata), values.yaml (config), templates/ (K8s manifests), charts/ (dependencies), README.md (docs).

**Q: How do you rollback a failed Helm release?**
> `helm rollback <release-name> <revision>` or just `helm rollback <release-name>` for previous version.

**Q: What's the difference between Helm 2 and Helm 3?**
> - Helm 2: Uses Tiller (server-side component), security issues
> - Helm 3: No Tiller, better security, 3-way merge, CRD support

**Q: What are CRDs?**
> Custom Resource Definitions extend Kubernetes API with custom resource types.

**Q: What is an Operator?**
> An Operator is software that uses CRDs and controllers to automate management of complex applications.

**Q: When would you use an Operator vs Helm?**
> - **Helm**: Stateless apps, simple deployments
> - **Operator**: Stateful apps, complex day-2 operations (backups, scaling, upgrades)

**Q: How do Helm hooks work?**
> Hooks run at specific lifecycle points (pre/post install/upgrade/delete) to execute jobs like DB migrations or cleanups.

**Q: What is the Operator SDK?**
> Framework by Red Hat to build Operators using Go, Ansible, or Helm.
