## 📚 **Theory & Q&A**

### 1. How can you deploy apps automatically with CI/CD?

> **CI/CD** automates the process of building, testing, and deploying applications to Kubernetes.

**Popular CI/CD Tools for Kubernetes:**
- **GitHub Actions** - Cloud-native, integrated with GitHub
- **GitLab CI/CD** - Built into GitLab
- **Jenkins** - Widely adopted, extensible
- **ArgoCD** - GitOps, declarative
- **Flux** - GitOps, CNCF project
- **Tekton** - Kubernetes-native pipelines
- **CircleCI** - Cloud CI/CD
- **Travis CI** - Open source friendly

**Typical CI/CD Pipeline:**
```
Code Commit → Build Docker Image → Push to Registry → Deploy to K8s → Run Tests
```

**Example GitHub Actions Workflow:**
```yaml
name: Deploy to Kubernetes
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v3
    
    - name: Build Docker image
      run: docker build -t myapp:${{ github.sha }} .
    
    - name: Push to registry
      run: |
        echo "${{ secrets.DOCKER_PASSWORD }}" | docker login -u "${{ secrets.DOCKER_USERNAME }}" --password-stdin
        docker push myapp:${{ github.sha }}
    
    - name: Deploy to Kubernetes
      run: |
        kubectl set image deployment/myapp myapp=myapp:${{ github.sha }}
```

### 2. What is ArgoCD?

> **ArgoCD** is a declarative, GitOps continuous delivery tool for Kubernetes.

**Key Concepts:**
- **GitOps**: Git as single source of truth
- **Declarative**: Desired state in Git
- **Automated**: Sync Git → Kubernetes
- **Auditable**: Git history = deployment history

**How ArgoCD Works:**
1. Manifests stored in Git
2. ArgoCD monitors Git repository
3. Detects changes
4. Syncs to Kubernetes cluster
5. Reports sync status

**Benefits:**
- ✅ Version control for deployments
- ✅ Easy rollback (git revert)
- ✅ Multi-cluster management
- ✅ Visual UI
- ✅ Automated sync
- ✅ Drift detection

### 3. What are ServiceAccounts?

> **ServiceAccount** provides an identity for processes running in Pods to access the Kubernetes API.

**Default Behavior:**
- Every namespace has a `default` ServiceAccount
- Pods use `default` SA if not specified
- SA gets a token mounted at `/var/run/secrets/kubernetes.io/serviceaccount/token`

**Use Cases:**
- CI/CD pipelines accessing K8s API
- Monitoring tools
- Operators
- Custom controllers

**Example:**
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-sa
  namespace: default
---
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  serviceAccountName: my-sa
  containers:
  - name: app
    image: nginx
```

**Disabling Auto-Mount:**
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-sa
automountServiceAccountToken: false
```

### 4. What is RBAC?

> **RBAC** (Role-Based Access Control) defines **who can do what** in a Kubernetes cluster.

**Components:**
1. **Role / ClusterRole** - Defines permissions (what)
2. **RoleBinding / ClusterRoleBinding** - Binds permissions to subjects (who)
3. **Subject** - User, Group, or ServiceAccount

**Scope:**
- **Role + RoleBinding** - Namespaced
- **ClusterRole + ClusterRoleBinding** - Cluster-wide

**Example:**
```yaml
# Role - what permissions
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]

---
# RoleBinding - who gets permissions
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
- kind: ServiceAccount
  name: my-sa
  namespace: default
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**Common Verbs:**
- `get`, `list`, `watch` - Read
- `create`, `update`, `patch` - Write
- `delete`, `deletecollection` - Delete
- `*` - All

### 5. How do you monitor a Kubernetes cluster?

**Monitoring Stack:**
- **Metrics**: Prometheus
- **Visualization**: Grafana
- **Logs**: Loki / ELK Stack
- **Traces**: Jaeger / Tempo
- **Alerts**: Alertmanager

**Key Metrics to Monitor:**
1. **Node Metrics**:
   - CPU, Memory, Disk usage
   - Network I/O
   
2. **Pod Metrics**:
   - CPU/Memory usage
   - Restart count
   - Ready status
   
3. **Cluster Metrics**:
   - API server latency
   - etcd health
   - Scheduler performance
   
4. **Application Metrics**:
   - Request rate
   - Error rate
   - Response time

**Tools:**
```bash
# Install Prometheus + Grafana
helm install prometheus prometheus-community/kube-prometheus-stack -n monitoring --create-namespace

# Access Grafana
kubectl port-forward -n monitoring svc/prometheus-grafana 3000:80

# Access Prometheus
kubectl port-forward -n monitoring svc/prometheus-kube-prometheus-prometheus 9090:9090
```

### 6. What are Admission Controllers?

> **Admission Controllers** intercept API requests **before they're persisted** to validate or modify them.

**Phases:**
1. **Authentication** - Who are you?
2. **Authorization** (RBAC) - What can you do?
3. **Admission Control** - Should this be allowed/modified?
4. **Persistence** - Save to etcd

**Types:**
- **Validating** - Validate requests (allow/deny)
- **Mutating** - Modify requests (add defaults)

**Common Admission Controllers:**
- `PodSecurityAdmission` - Enforce security standards
- `LimitRanger` - Enforce resource limits
- `ResourceQuota` - Enforce quotas
- `NamespaceLifecycle` - Prevent deletion of system namespaces
- `DefaultStorageClass` - Add default storage class

**Example - Mutating Webhook:**
```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingWebhookConfiguration
metadata:
  name: pod-label-injector
webhooks:
- name: inject.example.com
  clientConfig:
    service:
      name: label-injector
      namespace: default
      path: "/mutate"
  rules:
  - operations: ["CREATE"]
    apiGroups: [""]
    apiVersions: ["v1"]
    resources: ["pods"]
```

### 7. What is etcd?

> **etcd** is a distributed key-value store that stores the **entire cluster state**.

**What's Stored:**
- All Kubernetes objects (Pods, Services, etc.)
- Cluster configuration
- Secrets (encrypted if configured)
- State data

**Critical for:**
- ✅ Cluster state persistence
- ✅ Configuration management
- ✅ Service discovery
- ✅ Distributed locking

**Best Practices:**
- ✅ Run in HA mode (3 or 5 nodes)
- ✅ Backup regularly
- ✅ Enable encryption at rest
- ✅ Secure with TLS
- ✅ Monitor performance

**Backup etcd:**
```bash
ETCDCTL_API=3 etcdctl snapshot save backup.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
```

**Restore etcd:**
```bash
ETCDCTL_API=3 etcdctl snapshot restore backup.db \
  --data-dir=/var/lib/etcd-restore
```

### 8. How do you secure etcd?

**Security Measures:**

**1. TLS Encryption:**
- Client-to-server communication
- Peer-to-peer communication

**2. Authentication:**
- Client certificates
- Token-based auth

**3. Encryption at Rest:**
```yaml
# /etc/kubernetes/manifests/kube-apiserver.yaml
--encryption-provider-config=/etc/kubernetes/encryption-config.yaml
```

**Encryption Config:**
```yaml
apiVersion: apiextensions.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources:
  - secrets
  providers:
  - aescbc:
      keys:
      - name: key1
        secret: <base64-encoded-secret>
  - identity: {}
```

**4. Access Control:**
- Restrict network access
- Firewall rules
- RBAC for API access

**5. Monitoring:**
- Monitor etcd metrics
- Alert on high latency
- Track disk usage

### 9. What is Pod Security Admission?

> **Pod Security Admission** (PSA) enforces **security standards** at the namespace level.

**Replaces:** PodSecurityPolicy (deprecated in 1.25)

**Security Standards:**
1. **Privileged** - Unrestricted (not recommended)
2. **Baseline** - Minimal restrictions
3. **Restricted** - Heavily restricted (best practice)

**Modes:**
- `enforce` - Reject violating pods
- `audit` - Log violations
- `warn` - Show warnings

**Example:**
```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
```

**Restricted Standard Blocks:**
- Running as root
- Privileged containers
- Host network/PID/IPC
- Dangerous capabilities
- Host path volumes

### 10. How would you implement zero-downtime deployments?

**Strategies:**

**1. Rolling Updates (Default)**
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

**2. Blue-Green Deployment**
- Deploy new version (green)
- Test green
- Switch Service to green
- Keep blue for rollback

**3. Canary Deployment**
- Deploy new version to small subset
- Monitor metrics
- Gradually increase traffic
- Rollback if issues

**4. Prerequisites:**
- ✅ Readiness probes configured
- ✅ Pod Disruption Budget set
- ✅ Sufficient resources
- ✅ Health checks working
- ✅ Graceful shutdown

**Example with PDB:**
```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: myapp-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: myapp
```

### 12. Secret Management Best Practices

**❌ Don't:**
- Store secrets in Git
- Use base64 as encryption
- Share secrets across namespaces unnecessarily
- Leave secrets in pod environment variables

**✅ Do:**
- Use external secret managers (Vault, AWS Secrets Manager)
- Enable encryption at rest
- Use RBAC to restrict access
- Rotate secrets regularly
- Mount as volumes (not env vars)
- Use tools like:
  - **External Secrets Operator**
  - **Sealed Secrets**
  - **SOPS**

**Example - External Secrets:**
```yaml
apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: vault-backend
spec:
  provider:
    vault:
      server: "http://vault:8200"
      path: "secret"
      version: "v2"
      auth:
        tokenSecretRef:
          name: vault-token
          key: token
---
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: app-secret
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: SecretStore
  target:
    name: app-secret
  data:
  - secretKey: password
    remoteRef:
      key: database
      property: password
```

## 🔥 **Pro Tips & Best Practices**

### CI/CD
✅ **DO:**
- Use GitOps (ArgoCD, Flux)
- Automate testing
- Build immutable images
- Tag images with commit SHA
- Use separate environments (dev, staging, prod)

❌ **DON'T:**
- Deploy directly with kubectl
- Use `latest` tag
- Skip testing
- Deploy to production without staging
- Store credentials in pipeline code

### Monitoring
✅ **DO:**
- Monitor the 4 Golden Signals (latency, traffic, errors, saturation)
- Set up alerts
- Use dashboards
- Monitor application AND infrastructure
- Set SLOs and SLIs

❌ **DON'T:**
- Alert on everything (alert fatigue)
- Ignore logs
- Monitor only infrastructure
- Forget to monitor etcd

### Security
✅ **DO:**
- Use RBAC with least privilege
- Enable Pod Security Admission
- Scan images for vulnerabilities
- Use NetworkPolicies
- Encrypt etcd
- Rotate credentials
- Use ServiceAccounts properly

❌ **DON'T:**
- Run as root
- Use privileged containers
- Allow all traffic
- Store secrets in Git
- Use default ServiceAccount for apps
- Disable admission controllers

## 📝 **Common Interview Questions**

**Q: What is GitOps?**
> GitOps uses Git as single source of truth for declarative infrastructure and applications. Changes in Git trigger automated deployments.

**Q: Difference between ArgoCD and Flux?**
> Both are GitOps tools. ArgoCD has better UI, Flux is more lightweight and CNCF project.

**Q: What are the components of RBAC?**
> Role/ClusterRole (permissions), RoleBinding/ClusterRoleBinding (assignment), Subject (user/group/SA).

**Q: How does Prometheus work?**
> Prometheus scrapes metrics from targets, stores time-series data, and allows querying with PromQL.

**Q: What is the difference between authentication and authorization?**
> Authentication = Who you are (identity)
> Authorization = What you can do (permissions/RBAC)

**Q: How do you secure a Kubernetes cluster?**
> - Enable RBAC
> - Use NetworkPolicies
> - Pod Security Admission
> - Encrypt etcd
> - Scan images
> - Use ServiceAccounts
> - Regular updates

**Q: What is a ServiceAccount token?**
> JWT token mounted in pods that allows authentication to Kubernetes API.

**Q: Explain the 4 Golden Signals.**
> 1. Latency - Response time
> 2. Traffic - Request volume
> 3. Errors - Error rate
> 4. Saturation - Resource usage
