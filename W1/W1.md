# 🗓️ **WEEK 1 – Core Concepts (Pods, Deployments, Services)**

## 📚 **Theory & Q&A**

### 1. What is Kubernetes?

> **Kubernetes** (K8s) is an open-source **container orchestration platform** that automates deployment, scaling, and management of containerized applications.

**Key Features:**
- ✅ **Automated Deployment** - Deploy containers automatically
- ✅ **Self-Healing** - Restart failed containers
- ✅ **Auto-Scaling** - Scale based on load
- ✅ **Load Balancing** - Distribute traffic across Pods
- ✅ **Rolling Updates** - Zero-downtime deployments
- ✅ **Service Discovery** - Internal DNS for services

**Why Kubernetes?**
- Manage 100s of containers easily
- Works across clouds (AWS, GCP, Azure)
- Industry standard (CNCF project)
- Huge ecosystem and community

**Kubernetes vs Docker:**
- **Docker** - Container runtime
- **Kubernetes** - Container orchestrator (manages many containers)

---

### 2. What is a Pod?

> A **Pod** is the **smallest deployable unit** in Kubernetes.
> 
> It can contain **one or more containers** that share:
> - Network namespace (same IP address)
> - Storage volumes
> - Configuration

**Pod Characteristics:**
- Ephemeral (temporary) - can be deleted and recreated
- Each Pod gets unique IP address
- Containers in Pod communicate via localhost
- Scheduled on nodes as a unit

**Single Container vs Multi-Container Pod:**

**Single Container (Most Common):**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
spec:
  containers:
  - name: nginx
    image: nginx:1.24
    ports:
    - containerPort: 80
```

**Multi-Container (Sidecar Pattern):**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-with-logging
spec:
  containers:
  # Main application
  - name: web-app
    image: nginx:1.24
    ports:
    - containerPort: 80
    volumeMounts:
    - name: logs
      mountPath: /var/log/nginx
  
  # Logging sidecar
  - name: log-shipper
    image: fluent/fluentd:latest
    volumeMounts:
    - name: logs
      mountPath: /var/log/nginx
  
  volumes:
  - name: logs
    emptyDir: {}
```

**Use Cases for Multi-Container Pods:**
1. **Sidecar** - Helper container (logging, monitoring)
2. **Ambassador** - Proxy to external services
3. **Adapter** - Transform/normalize data

---

### 3. What's the difference between a Pod and a Container?

| Aspect              | Container                       | Pod                              |
| ------------------- | ------------------------------- | -------------------------------- |
| **Definition**      | Running instance of an image    | Wrapper around container(s)      |
| **Scheduling**      | Not directly scheduled          | Scheduled by Kubernetes          |
| **Network**         | Own network namespace           | Shared network namespace         |
| **IP Address**      | Not directly assigned           | Gets unique IP                   |
| **Lifecycle**       | Managed by runtime (Docker)     | Managed by Kubernetes            |
| **Count**           | One container                   | One or more containers           |

**Key Point:** Kubernetes schedules **Pods**, not individual containers.

### 4. What is a Deployment?

> **Deployment** is a higher-level abstraction that manages **Pods** and **ReplicaSets**.

**What Deployment Does:**
- ✅ Creates and manages ReplicaSets
- ✅ Ensures desired number of Pods running
- ✅ Handles rolling updates
- ✅ Enables rollbacks
- ✅ Scales Pods up/down

**Deployment Hierarchy:**
```
Deployment
    ↓
ReplicaSet
    ↓
Pod → Pod → Pod
```

**Example:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3  # Desired number of Pods
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.24
        ports:
        - containerPort: 80
```

**Key Benefits:**
- Declarative (you specify desired state)
- Self-healing (recreates failed Pods)
- Version control (rollback capability)

### 5. What is a ReplicaSet?

> **ReplicaSet** ensures a specified number of **identical Pods** are running at all times.

**How it works:**
1. You specify desired replica count
2. ReplicaSet monitors running Pods
3. If Pod dies, creates new one
4. If too many Pods, deletes extras

**Example:**
```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: nginx-replicaset
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.24
```

**Important:** You usually **don't create ReplicaSets directly** - use Deployments instead!

**Deployment vs ReplicaSet:**
- **Deployment** - Manages ReplicaSets, handles updates/rollbacks
- **ReplicaSet** - Only ensures Pod count, no update strategy

### 6. What is a Service in Kubernetes?

> **Service** provides a **stable network endpoint** to access Pods, even when Pod IPs change.

**Why Services?**
- Pods are ephemeral (IPs change on restart)
- Need stable way to access Pods
- Load balance across multiple Pods

**How Services Work:**
- Uses **labels** to select Pods
- Creates stable DNS name
- Load balances traffic
- Maintained by kube-proxy

**Service Discovery:**
```
Service Name: nginx-service
DNS: nginx-service.default.svc.cluster.local
ClusterIP: 10.96.0.10
```

**Basic Service:**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  selector:
    app: nginx  # Selects Pods with this label
  ports:
  - port: 80        # Service port
    targetPort: 80  # Pod port
```

### 7. Types of Services

#### **1. ClusterIP (Default)**
**Exposes service internally within cluster**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: backend-service
spec:
  type: ClusterIP
  selector:
    app: backend
  ports:
  - port: 8080
    targetPort: 8080
```

**Use Case:** Internal microservices communication

---

#### **2. NodePort**
**Exposes service on each Node's IP at a static port (30000-32767)**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: frontend-service
spec:
  type: NodePort
  selector:
    app: frontend
  ports:
  - port: 80
    targetPort: 80
    nodePort: 30080  # Optional, auto-assigned if omitted
```

**Access:** `http://<NodeIP>:30080`

**Use Case:** Development, testing, on-premises

---

#### **3. LoadBalancer**
**Creates external load balancer (cloud provider)**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80
```

**Use Case:** Production apps on cloud (AWS ELB, GCP LB)

---

#### **4. ExternalName**
**Maps service to external DNS name**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-database
spec:
  type: ExternalName
  externalName: database.example.com
```

**Use Case:** Access external services via Kubernetes DNS

---

### Comparison Table

| Type          | Scope      | Port Range     | Cloud LB | Use Case          |
| ------------- | ---------- | -------------- | -------- | ----------------- |
| ClusterIP     | Internal   | Any            | No       | Inter-service     |
| NodePort      | External   | 30000-32767    | No       | Dev/Testing       |
| LoadBalancer  | External   | Any            | Yes      | Production        |
| ExternalName  | External   | N/A            | No       | External services |

### 8. What is `kubectl`?

> **kubectl** is the command-line tool to interact with **Kubernetes API Server**.

**Common Commands:**

```bash
# Cluster info
kubectl cluster-info
kubectl get nodes

# Create resources
kubectl create -f pod.yaml
kubectl apply -f deployment.yaml

# Get resources
kubectl get pods
kubectl get deployments
kubectl get services

# Describe (detailed info)
kubectl describe pod nginx
kubectl describe service nginx-service

# Logs
kubectl logs nginx
kubectl logs -f nginx  # Follow logs

# Execute commands
kubectl exec -it nginx -- bash

# Delete resources
kubectl delete pod nginx
kubectl delete -f deployment.yaml

# Scale
kubectl scale deployment nginx --replicas=5
```

**Useful Flags:**
- `-n namespace` - Specify namespace
- `-o yaml` - Output as YAML
- `-o wide` - More details
- `--watch` or `-w` - Watch for changes
- `-A` or `--all-namespaces` - All namespaces

---

### 9. What's the difference between `kubectl apply` and `create`?

| Command          | Type        | Behavior                           | Update?    |
| ---------------- | ----------- | ---------------------------------- | ---------- |
| `kubectl create` | Imperative  | Creates resource, fails if exists  | No         |
| `kubectl apply`  | Declarative | Creates or updates resource        | Yes        |

**Examples:**

```bash
# Create (fails if exists)
kubectl create -f nginx-pod.yaml
# Error: pod "nginx" already exists

# Apply (creates or updates)
kubectl apply -f nginx-pod.yaml
# pod/nginx created (or configured)
```

**Best Practice:** Use `kubectl apply` for GitOps and infrastructure-as-code.

### 10. What is a Namespace?

> **Namespace** is a logical partition to isolate resources within a cluster.

**Default Namespaces:**
- `default` - Default namespace for resources
- `kube-system` - Kubernetes system components
- `kube-public` - Publicly accessible
- `kube-node-lease` - Node heartbeat data

**Why Use Namespaces?**
- ✅ Organize resources (dev, staging, prod)
- ✅ Apply resource quotas
- ✅ Set RBAC policies
- ✅ Isolate teams/projects

**Example:**
```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
```

**Using Namespaces:**
```bash
# Create namespace
kubectl create namespace production

# Create resource in namespace
kubectl apply -f deployment.yaml -n production

# Get resources from namespace
kubectl get pods -n production

# Get all namespaces
kubectl get namespaces

# Set default namespace
kubectl config set-context --current --namespace=production
```

**Resource with Namespace:**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
  namespace: production
spec:
  containers:
  - name: nginx
    image: nginx:1.24
```

## 🔥 **Pro Tips & Best Practices**

### Pods
✅ **DO:**
- Use Deployments instead of bare Pods
- Set resource limits
- Use health checks (covered in Week 3)
- Use meaningful labels

❌ **DON'T:**
- Create Pods directly in production
- Run multiple unrelated containers in one Pod
- Use `:latest` tag in production

### Deployments
✅ **DO:**
- Always use Deployments (not bare Pods/ReplicaSets)
- Set proper replicas for high availability
- Use rolling updates
- Add annotations for change tracking

❌ **DON'T:**
- Manually create ReplicaSets
- Skip replica count (set at least 2 for HA)
- Update images without proper testing

### Services
✅ **DO:**
- Use ClusterIP for internal services
- Use meaningful service names
- Match selector labels with Pod labels
- Use Ingress instead of multiple LoadBalancers

❌ **DON'T:**
- Use NodePort in production
- Forget to set selectors correctly
- Create unnecessary LoadBalancers (expensive)

## 📝 **Common Interview Questions**

**Q: What is the difference between a Pod and a Container?**
> A Container is the actual running environment (like Docker), while a Pod is a Kubernetes abstraction that wraps one or more containers and provides shared networking and storage.

**Q: Why use Deployments instead of Pods?**
> Deployments provide automatic scaling, self-healing, rolling updates, and rollback capabilities. Bare Pods don't get recreated if they fail.

**Q: Can a Service exist without Pods?**
> Yes, but it won't route traffic anywhere. The Service will have no endpoints until matching Pods are created.

**Q: What happens if a Pod crashes?**
> - If managed by Deployment/ReplicaSet: Automatically recreated
> - If bare Pod: Stays dead, manual recreation needed

**Q: How does Service discover Pods?**
> Services use **label selectors** to find Pods. Any Pod with matching labels becomes an endpoint for the Service.

**Q: What is the difference between targetPort and port in a Service?**
> - `port` - Service port (what clients connect to)
> - `targetPort` - Pod port (where container is listening)

**Q: Can you access a ClusterIP Service from outside?**
> No, ClusterIP is internal only. Use NodePort, LoadBalancer, or Ingress for external access.

**Q: What is a headless Service?**
> A Service with `clusterIP: None` that returns Pod IPs directly instead of a single Service IP. Used for StatefulSets.

**Q: What command shows you all resources in a namespace?**
```bash
kubectl get all -n namespace-name
```

**Q: How do you check if a Pod is running?**
```bash
kubectl get pods
kubectl describe pod <pod-name>
kubectl logs <pod-name>
```

## 🎯 **kubectl Command Cheat Sheet**

### Basic Commands
```bash
# Get resources
kubectl get pods
kubectl get deployments
kubectl get services
kubectl get all

# Describe (detailed info)
kubectl describe pod nginx
kubectl describe deployment nginx-deployment

# Create from file
kubectl create -f nginx-pod.yaml
kubectl apply -f nginx-deployment.yaml

# Delete
kubectl delete pod nginx
kubectl delete deployment nginx-deployment
kubectl delete -f nginx-pod.yaml
```

### Pod Management
```bash
# Create pod (imperative)
kubectl run nginx --image=nginx:1.24 --port=80

# Get pod details
kubectl get pods -o wide
kubectl get pod nginx -o yaml

# Execute command in pod
kubectl exec nginx -- ls /
kubectl exec -it nginx -- bash

# View logs
kubectl logs nginx
kubectl logs -f nginx  # Follow logs
kubectl logs nginx --tail=20
kubectl logs nginx --since=1h
```

### Deployment Management
```bash
# Create deployment
kubectl create deployment nginx --image=nginx:1.24 --replicas=3

# Scale deployment
kubectl scale deployment nginx --replicas=5

# Update image
kubectl set image deployment/nginx nginx=nginx:1.25

# Rollout status
kubectl rollout status deployment nginx

# Rollout history
kubectl rollout history deployment nginx

# Rollback
kubectl rollout undo deployment nginx
```

### Service Management
```bash
# Expose deployment
kubectl expose deployment nginx --port=80 --type=NodePort

# Get service details
kubectl get svc
kubectl describe svc nginx

# Get service endpoints
kubectl get endpoints nginx
```

### Namespace Management
```bash
# Create namespace
kubectl create namespace production

# List namespaces
kubectl get namespaces

# Set default namespace
kubectl config set-context --current --namespace=production

# Delete namespace (deletes all resources in it!)
kubectl delete namespace production
```

### Debugging
   ```bash
# Get events
kubectl get events
kubectl get events --sort-by='.lastTimestamp'

# Describe (troubleshooting)
kubectl describe pod nginx

# Logs
kubectl logs nginx
kubectl logs nginx --previous  # Previous container logs

# Port forward
kubectl port-forward pod/nginx 8080:80

# Execute commands
kubectl exec -it nginx -- bash
```
