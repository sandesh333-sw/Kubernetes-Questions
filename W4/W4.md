# 🗓️ **WEEK 4 – Ingress, Networking, and Load Balancing**

## 📚 **Theory & Q&A**

### 1. What is an Ingress?

> **Ingress** is a Kubernetes resource that manages **external HTTP/HTTPS access** to services in a cluster.
> 
> It provides:
> - **HTTP/HTTPS routing** based on hostnames and paths
> - **TLS/SSL termination**
> - **Name-based virtual hosting**
> - **Load balancing**

**Without Ingress:**
- Need LoadBalancer Service for each app (expensive)
- No path-based routing
- No TLS management

**With Ingress:**
- Single entry point for multiple services
- Smart HTTP routing
- Centralized TLS/SSL

---

### 2. What's the difference between Service and Ingress?

| Feature                      | Service                        | Ingress                            |
| ---------------------------- | ------------------------------ | ---------------------------------- |
| **Layer**                    | L4 (TCP/UDP)                   | L7 (HTTP/HTTPS)                    |
| **Scope**                    | Network endpoint               | HTTP routing layer                 |
| **Path-based routing**       | ❌ No                           | ✅ Yes                              |
| **Host-based routing**       | ❌ No                           | ✅ Yes                              |
| **TLS termination**          | ❌ No                           | ✅ Yes                              |
| **Load balancing**           | Round-robin (kube-proxy)       | Advanced (controller-dependent)    |
| **Use case**                 | Internal/external TCP access   | HTTP/HTTPS routing & SSL           |

**Example:**
```
Internet
   ↓
Ingress (myapp.com/api → api-service, myapp.com/web → web-service)
   ↓
Services (api-service, web-service)
   ↓
Pods
```

---

### 3. What is an Ingress Controller?

> **Ingress Controller** is a load balancer that **implements the Ingress API**.
> 
> Kubernetes doesn't come with one by default - you must install it.

**Popular Ingress Controllers:**
- **Nginx Ingress** - Most popular, feature-rich
- **Traefik** - Modern, dynamic configuration
- **HAProxy** - High performance
- **AWS ALB Ingress** - AWS Application Load Balancer
- **GCE Ingress** - Google Cloud Load Balancer
- **Contour** - Envoy-based
- **Kong** - API Gateway features

**How it works:**
1. Watch Ingress resources
2. Configure load balancer based on Ingress rules
3. Route traffic to backend Services

---

### 4. Basic Ingress Example

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
spec:
  # Optional: default backend (404 handler)
  defaultBackend:
    service:
      name: default-backend
      port:
        number: 80
  
  # Routing rules
  rules:
  - host: myapp.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80
```

---

### 5. Path Types in Ingress

| Path Type             | Matching Behavior                    | Example                        |
| --------------------- | ------------------------------------ | ------------------------------ |
| `Exact`               | Exact match only                     | `/api` matches only `/api`     |
| `Prefix`              | Matches prefix                       | `/api` matches `/api`, `/api/*`|
| `ImplementationSpecific` | Depends on Ingress Controller        | Varies                         |

**Example:**
```yaml
paths:
- path: /api
  pathType: Exact      # Only /api
  backend: ...

- path: /static
  pathType: Prefix     # /static, /static/, /static/image.jpg
  backend: ...
```

### 6. TLS/SSL with Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: tls-ingress
spec:
  tls:
  - hosts:
    - myapp.com
    - www.myapp.com
    secretName: tls-secret  # Contains tls.crt and tls.key
  
  rules:
  - host: myapp.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80
```

**Create TLS Secret:**
```bash
kubectl create secret tls tls-secret \
  --cert=path/to/tls.crt \
  --key=path/to/tls.key
```

### 7. What is kube-proxy?

> **kube-proxy** is a network component that runs on each node and manages **Service networking**.

**Responsibilities:**
- Maintains network rules for Services
- Routes traffic from Service IP to Pods
- Implements load balancing across Pod endpoints

**Modes:**
1. **iptables** (default) - Uses iptables rules
2. **IPVS** - High performance, better load balancing
3. **userspace** - Legacy, slow

**How it works:**
```
Client → Service IP (ClusterIP)
  ↓
kube-proxy (iptables/IPVS rules)
  ↓
Pod IP (random Pod selected)
```

---

### 8. How does DNS work in Kubernetes?

> Kubernetes has an internal DNS server (**CoreDNS**) that provides DNS resolution for Services and Pods.

**Service DNS Format:**
```
<service-name>.<namespace>.svc.cluster.local
```

**Examples:**
- `web-service` (same namespace)
- `web-service.default` (specific namespace)
- `web-service.default.svc.cluster.local` (FQDN)

**Pod DNS Format:**
```
<pod-ip-with-dashes>.<namespace>.pod.cluster.local
```

Example: `10-244-1-5.default.pod.cluster.local`

**StatefulSet DNS:**
```
<pod-name>.<service-name>.<namespace>.svc.cluster.local
```

Example: `mysql-0.mysql.default.svc.cluster.local`

### 9. What is the difference between NodePort and LoadBalancer?

| Feature           | NodePort                           | LoadBalancer                        |
| ----------------- | ---------------------------------- | ----------------------------------- |
| **Access**        | `<NodeIP>:<NodePort>`              | External IP (cloud LB)              |
| **Port range**    | 30000-32767 (default)              | Standard (80, 443)                  |
| **Load balancing**| Manual (client-side)               | Automatic (cloud provider)          |
| **Cost**          | Free                               | Cloud provider charges              |
| **Use case**      | Development, testing               | Production (cloud)                  |
| **Availability**  | Any environment                    | Cloud providers only                |

**NodePort Example:**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp-nodeport
spec:
  type: NodePort
  selector:
    app: myapp
  ports:
  - port: 80
    targetPort: 8080
    nodePort: 30080  # Optional, auto-assigned if omitted
```

**LoadBalancer Example:**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp-lb
spec:
  type: LoadBalancer
  selector:
    app: myapp
  ports:
  - port: 80
    targetPort: 8080
```

### 10. What are Labels and Selectors?

> **Labels** are key-value pairs attached to objects (Pods, Services, etc.).
> **Selectors** use labels to select objects.

**Labels Example:**
```yaml
metadata:
  labels:
    app: nginx
    environment: production
    tier: frontend
    version: v1.0
```

**Selector Types:**

**1. Equality-based:**
```yaml
selector:
  app: nginx
  tier: frontend
```

**2. Set-based:**
```yaml
selector:
  matchLabels:
    app: nginx
  matchExpressions:
  - key: tier
    operator: In
    values: [frontend, backend]
  - key: environment
    operator: NotIn
    values: [dev]
```

**Common Uses:**
- Services select Pods
- Deployments manage Pods
- NetworkPolicies target Pods
- Node affinity

### 11. What is NetworkPolicy?

> **NetworkPolicy** controls network traffic between Pods (like a firewall).

**By default:** All Pods can communicate with all Pods.

**With NetworkPolicy:** You can restrict:
- Which Pods can talk to which Pods
- Which namespaces can access your Pods
- Which external IPs can access your Pods

**Example - Deny all ingress:**
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-ingress
  namespace: production
spec:
  podSelector: {}  # Apply to all pods in namespace
  policyTypes:
  - Ingress
```

**Example - Allow specific traffic:**
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
```

**Note:** Requires a CNI plugin that supports NetworkPolicy (Calico, Cilium, Weave).

### 12. What are Taints and Tolerations?

> **Taints** repel Pods from nodes.
> **Tolerations** allow Pods to be scheduled on tainted nodes.

**Use Cases:**
- Dedicate nodes to specific workloads
- Keep nodes for special hardware (GPU)
- Isolate production from dev
- Node maintenance

**Taint a Node:**
```bash
kubectl taint nodes node1 key=value:NoSchedule
```

**Taint Effects:**
- `NoSchedule` - Don't schedule new Pods
- `PreferNoSchedule` - Try not to schedule
- `NoExecute` - Evict existing Pods

**Toleration in Pod:**
```yaml
tolerations:
- key: "key"
  operator: "Equal"
  value: "value"
  effect: "NoSchedule"
```

**Example:**
```bash
# Taint node for GPU workloads
kubectl taint nodes gpu-node gpu=true:NoSchedule

# Pod with toleration
tolerations:
- key: "gpu"
  operator: "Equal"
  value: "true"
  effect: "NoSchedule"
```

### 13. How do Pods communicate internally?

> Kubernetes uses a **flat network** where every Pod gets a unique IP address.

**Network Model Requirements:**
1. All Pods can communicate with all other Pods without NAT
2. All nodes can communicate with all Pods without NAT
3. The IP a Pod sees itself as is the same IP others see it as

**Communication:**
- **Pod to Pod (same node):** Direct via virtual bridge
- **Pod to Pod (different node):** Via overlay network (CNI plugin)
- **Pod to Service:** Via kube-proxy (iptables/IPVS)
- **Pod to external:** Via NAT

**CNI Plugins (Container Network Interface):**
- **Calico** - L3 networking, NetworkPolicy support
- **Flannel** - Simple overlay network
- **Weave** - Mesh network
- **Cilium** - eBPF-based, advanced features
- **Canal** - Flannel + Calico policies

### 14. Service Types Summary

| Type          | Scope      | Use Case                        | Access Method                 |
| ------------- | ---------- | ------------------------------- | ----------------------------- |
| ClusterIP     | Internal   | Inter-service communication     | `<service>.<namespace>`       |
| NodePort      | External   | Development, on-prem            | `<NodeIP>:<NodePort>`         |
| LoadBalancer  | External   | Production (cloud)              | External IP (cloud LB)        |
| ExternalName  | External   | DNS alias to external service   | DNS CNAME                     |

**ClusterIP (default):**
```yaml

```

**NodePort:**
```yaml

- port: 80
  nodePort: 30080
```

**LoadBalancer:**
```yaml
type: LoadBalancer
```

**ExternalName:**
```yaml
type: ExternalName
externalName: external-service.example.com
```

### 15. What is Headless Service?

> **Headless Service** is a Service without ClusterIP (`clusterIP: None`).
> 
> Returns Pod IPs directly instead of Service IP.

**Use Cases:**
- StatefulSets (stable DNS per Pod)
- Service discovery without load balancing
- Client-side load balancing

**Example:**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: mysql
spec:
  clusterIP: None  # Headless
  selector:
    app: mysql
  ports:
  - port: 3306
```

**DNS Resolution:**
```
mysql.default.svc.cluster.local → Pod IPs (not Service IP)
mysql-0.mysql.default.svc.cluster.local → mysql-0 Pod IP
mysql-1.mysql.default.svc.cluster.local → mysql-1 Pod IP
```

## 🔥 **Pro Tips & Best Practices**

### Ingress
✅ **DO:**
- Use Ingress for HTTP/HTTPS routing
- Centralize TLS certificates
- Use path-based routing for microservices
- Add rate limiting and authentication (via annotations)

❌ **DON'T:**
- Use Ingress for non-HTTP traffic (use Service)
- Expose internal services unnecessarily
- Forget to install Ingress Controller first
- Use wildcards without proper security

### Networking
✅ **DO:**
- Use NetworkPolicies in production
- Start with deny-all, then allow specific traffic
- Use namespaces to isolate workloads
- Monitor network traffic

❌ **DON'T:**
- Leave cluster wide-open (default allow-all)
- Use hostNetwork unless necessary
- Expose Services unnecessarily
- Skip CNI plugin NetworkPolicy support check

### Services
✅ **DO:**
- Use ClusterIP for internal services
- Use LoadBalancer sparingly (cost)
- Use Ingress instead of multiple LoadBalancers
- Set appropriate session affinity if needed

❌ **DON'T:**
- Use NodePort in production
- Expose services to 0.0.0.0 unnecessarily
- Forget to set selectors correctly
- Use ExternalName for internal services

### Labels & Selectors
✅ **DO:**
- Use consistent naming conventions
- Include environment, tier, version
- Use for organization and automation
- Document label schema

❌ **DON'T:**
- Use too many labels (overwhelming)
- Change labels on running resources carelessly
- Use special characters (stick to alphanumeric + `-` + `_`)

## 📝 **Common Interview Questions**

**Q: Why do you need an Ingress Controller?**
> Ingress resource alone doesn't do anything. Ingress Controller reads Ingress resources and configures the actual load balancer.

**Q: Can you have multiple Ingress Controllers?**
> Yes! Use `ingressClassName` to specify which controller handles which Ingress.

**Q: How does kube-proxy load balance?**
> Round-robin selection of Pod endpoints. iptables mode uses random selection, IPVS supports multiple algorithms.

**Q: What happens if you don't specify a namespace in DNS query?**
> Uses the Pod's namespace by default.

**Q: Difference between Ingress and API Gateway?**
> Ingress: Basic L7 routing, TLS termination
> API Gateway: Advanced features (rate limiting, auth, transformations, monetization)

**Q: How do NetworkPolicies work with multiple CNIs?**
> NetworkPolicies are Kubernetes-native, but implementation depends on CNI plugin support.

**Q: Can you use Ingress for TCP/UDP traffic?**
> Standard Ingress: No (HTTP/HTTPS only)
> Some controllers support TCP/UDP via custom configurations (Nginx ConfigMap)

**Q: What is the difference between Taint and NodeSelector?**
> - **NodeSelector**: Positive selection (Pod chooses node)
> - **Taint**: Negative selection (Node repels Pods)
