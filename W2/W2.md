# 🗓️ **WEEK 2 – ConfigMaps, Secrets, and Volumes**

## 📚 **Theory & Q&A**

### 1. What is a ConfigMap?

> **ConfigMap** stores non-sensitive configuration data (e.g., environment variables, file paths, config files) in key-value format.
> 
> **Use Cases:**
> - Application configuration (database URLs, feature flags)
> - Environment-specific settings
> - Configuration files that need to be mounted

**Example:**
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DATABASE_URL: "postgres://db.example.com:5432/mydb"
  LOG_LEVEL: "info"
  app.properties: |
    max.connections=100
    timeout=30s
```

---

### 2. What is a Secret?

> **Secret** stores **sensitive** data like passwords, tokens, SSH keys, or TLS certificates.
> 
> **Important:** 
> - Data is base64 encoded (NOT encrypted by default!)
> - Enable encryption at rest in production
> - Use tools like Sealed Secrets or external secret managers (Vault, AWS Secrets Manager)

**Types of Secrets:**
- `Opaque` - arbitrary user-defined data (default)
- `kubernetes.io/tls` - TLS certificates
- `kubernetes.io/dockerconfigjson` - Docker registry credentials
- `kubernetes.io/basic-auth` - basic authentication
- `kubernetes.io/ssh-auth` - SSH credentials

**Example:**
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  username: YWRtaW4=        # base64 encoded "admin"
  password: cGFzc3dvcmQxMjM= # base64 encoded "password123"
```

---

### 3. How do you inject ConfigMap data into Pods?

There are **3 ways** to inject ConfigMap data:

#### **Method 1: As Environment Variables (Single Key)**
```yaml
env:
  - name: DATABASE_URL
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: DATABASE_URL
```

#### **Method 2: As Environment Variables (All Keys)**
```yaml
envFrom:
  - configMapRef:
      name: app-config
```

#### **Method 3: As Mounted Files**
```yaml
volumes:
  - name: config-volume
    configMap:
      name: app-config
volumeMounts:
  - name: config-volume
    mountPath: /etc/config
```

---

### 4. What are Volumes?

> **Volumes** provide **persistent storage** to Pods that survives container restarts.
> Without volumes, data is lost when a container crashes or restarts.

**Common Volume Types:**
- `emptyDir` - temporary storage, deleted when Pod is removed
- `hostPath` - mounts a directory from the node's filesystem
- `persistentVolumeClaim` - uses a PersistentVolume
- `configMap` / `secret` - mounts config/secret as files
- `nfs` - Network File System
- Cloud-specific: `awsElasticBlockStore`, `gcePersistentDisk`, `azureDisk`

---

### 5. Difference between emptyDir and PersistentVolume?

| Volume Type             | Lifetime                         | Use Case                          |
| ----------------------- | -------------------------------- | --------------------------------- |
| `emptyDir`              | Exists only while Pod is running | Temporary cache, scratch space    |
| `PersistentVolume` (PV) | Exists beyond Pod lifecycle      | Database storage, user uploads    |
| `hostPath`              | Tied to specific node            | Accessing node's logs, /var/run   |

**emptyDir Example:**
```yaml
volumes:
  - name: cache
    emptyDir: {}
```

**hostPath Example (use with caution!):**
```yaml
volumes:
  - name: docker-socket
    hostPath:
      path: /var/run/docker.sock
      type: Socket
```

---

### 6. What is a PersistentVolume (PV)?

> A **PersistentVolume (PV)** is a piece of storage in the cluster that has been provisioned by an admin or dynamically via **StorageClass**.
> 
> - It's a **cluster-level resource** (not namespaced)
> - Has a lifecycle independent of any Pod
> - Can be manually created or dynamically provisioned

**PV Lifecycle:**
1. **Provisioning** - Admin creates or dynamic provisioning
2. **Binding** - PVC binds to a matching PV
3. **Using** - Pod uses the PVC
4. **Reclaiming** - After PVC is deleted (Retain, Delete, Recycle)

**Access Modes:**
- `ReadWriteOnce (RWO)` - mounted as read-write by a single node
- `ReadOnlyMany (ROX)` - mounted as read-only by many nodes
- `ReadWriteMany (RWX)` - mounted as read-write by many nodes

**Example:**
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-example
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  hostPath:
    path: /mnt/data
```

---

### 7. What is a PersistentVolumeClaim (PVC)?

> A **PersistentVolumeClaim (PVC)** is a **user's request for storage**.
> 
> - Users create PVCs without knowing the underlying storage details
> - Kubernetes automatically binds PVC to a matching PV
> - Namespaced resource

**Example:**
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-example
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: standard
```

---

### 8. What's the relationship between PV and PVC?

```
┌─────────────┐      ┌─────────────┐      ┌─────────────┐
│   Storage   │ ───> │     PV      │ <─── │     PVC     │ <─── Pod
│  (Physical) │      │  (Cluster)  │      │ (Namespace) │
└─────────────┘      └─────────────┘      └─────────────┘
```

**Binding Process:**
1. Admin creates PV (or dynamic provisioning creates it)
2. User creates PVC requesting storage
3. Kubernetes finds a matching PV based on:
   - Storage size
   - Access modes
   - Storage class
4. PVC binds to PV (one-to-one binding)
5. Pod uses PVC in its volume definition

---

### 9. What's the use of `StorageClass`?

> **StorageClass** enables **dynamic provisioning** of PersistentVolumes.
> 
> Instead of admin manually creating PVs, StorageClass automatically provisions them when a PVC is created.

**Benefits:**
- No need to pre-create PVs
- Automatic provisioning based on demand
- Different storage tiers (fast SSD, slow HDD)

**Example:**
```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-storage
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
```

**Using StorageClass in PVC:**
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: fast-pvc
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-storage
  resources:
    requests:
      storage: 20Gi
```

### 10. How can you mount a Secret into a Pod?

**Method 1: As Environment Variables**
```yaml
env:
  - name: DB_USERNAME
    valueFrom:
      secretKeyRef:
        name: db-secret
        key: username
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-secret
        key: password
```

**Method 2: As Mounted Volume (More Secure)**
```yaml
volumes:
  - name: secret-volume
    secret:
      secretName: db-secret
volumeMounts:
  - name: secret-volume
    mountPath: /etc/secrets
    readOnly: true
```

Files created:
- `/etc/secrets/username`
- `/etc/secrets/password`

## 🔥 **Pro Tips & Best Practices**

### ConfigMaps
✅ **DO:**
- Use for non-sensitive configuration
- Keep configs separate from container images
- Version your ConfigMaps (append version to name)

❌ **DON'T:**
- Store passwords or sensitive data
- Make ConfigMaps too large (1MB limit)

### Secrets
✅ **DO:**
- Enable encryption at rest
- Use RBAC to restrict access
- Consider external secret managers (HashiCorp Vault, AWS Secrets Manager)
- Mount as volumes instead of env vars (more secure, can be updated)

❌ **DON'T:**
- Commit secrets to Git (use sealed-secrets or SOPS)
- Assume base64 = encrypted
- Use secrets in logs

### Volumes & Storage
✅ **DO:**
- Use PVCs instead of directly mounting hostPath
- Set appropriate reclaim policies (Retain for production data)
- Use StorageClass for dynamic provisioning
- Monitor storage usage

❌ **DON'T:**
- Use hostPath in production (ties Pod to specific node)
- Forget to set resource limits
- Use emptyDir for data that needs to persist

## 📝 **Common Interview Questions**

**Q: What happens if you update a ConfigMap that's mounted as a volume?**
> The files in the Pod are eventually updated (kubelet sync period ~60s). However, env vars are NOT updated automatically - requires Pod restart.

**Q: How do you encode/decode secrets?**
```bash
# Encode
echo -n "password123" | base64
# Output: cGFzc3dvcmQxMjM=

# Decode
echo "cGFzc3dvcmQxMjM=" | base64 -d
# Output: password123
```

**Q: What is the difference between Retain, Delete, and Recycle reclaim policies?**
- `Retain` - PV is kept after PVC deletion (manual cleanup required)
- `Delete` - PV and underlying storage are deleted
- `Recycle` - Deprecated (basic scrub: rm -rf /thevolume/*)

**Q: Can multiple PVCs bind to the same PV?**
> No! PV-PVC binding is 1:1. Use ReadWriteMany access mode if multiple Pods need to access the same storage.

**Q: How do you create a secret from literal values?**
```bash
kubectl create secret generic db-secret \
  --from-literal=username=admin \
  --from-literal=password=secretpass
```

**Q: How do you create a ConfigMap from a file?**
```bash
kubectl create configmap app-config \
  --from-file=app.properties \
  --from-file=config/
```
